# Архитектура и Стандарты Разработки: Узел крепления решетки составной колонны

Настоящий документ определяет жесткие архитектурные рамки, паттерны проектирования и правила модификации плагинов пакета «Сквозная колонна RAM» (включая генератор ствола и параметрические узлы) для платформы Tekla Structures 2022. Документ является обязательным руководством для разработчиков и внешних ИИ-агентов. Любые отклонения от описанной структуры являются дефектом архитектуры.

## 1. Компонентная Модель Данных и Пайплайн (Data Flow)

Плагины используют строгое разделение между плоскими данными диалогового окна Tekla и строго типизированной объектной моделью бизнес-логики.

### 1.1 Роль DTO-контейнеров (`PartSettings` и `BraceWrap`)
Запрещено передавать в методы сборки геометрии разрозненные строки профилей или материалов. Атрибуты всегда инкапсулируются:
- `PartSettings` — неделимый контейнер для создания физической детали Tekla (Профиль, Материал, Префиксы, Класс, UDA).
- `BraceWrap` — обертка для логических компонентов узла. Хранит ссылку на деталь, её векторы направлений, индивидуальные параметры швов ($h$, $e1$, $e2$) и её роль (IsTop, IsStrut).

### 1.2 Сквозной пайплайн передачи данных
Передача данных от интерфейса к модели происходит строго по следующей 5-ступенчатой цепочке:
1. **WPF View (`MainWindow.xaml` / `UIControls`)**: Биндинг элементов интерфейса к свойствам ViewModel.
2. **`MainWindowViewModel.cs`**: Плоские свойства с атрибутами `[StructuresDialog("FieldName", typeof(TD.Type))]`.
3. **`PluginData.cs`**: Плоские зеркальные поля с атрибутами `[StructuresField("FieldName")]`, считываемые ядром Tekla.
4. **Слой бизнес-модели (`Models/BuiltUpColumnData.cs` или `JointData.cs`)**: Чистые C# классы объектной модели. На этом уровне плоские поля заменяются на экземпляры DTO-объектов (`PartSettings`, `BraceWrap` и т.д.).
5. **`Services/PluginDataMapper.cs`**: Единственная точка сборки. Маппер обязан трансформировать плоский список из `PluginData` в объектную структуру исключительно через специализированные внутренние методы (например, `CreatePart` для деталей или `AddBraceSetting` для списков).

⚠️ **Чеклист при добавлении нового параметра.** Обязательно обновить все 4 точки:
1. `PluginData.cs` — поле с `[StructuresField]`
2. `MainWindowViewModel.cs` — свойство с `[StructuresDialog]`
3. Файл бизнес-модели (`JointData.cs` / `BuiltUpColumnData.cs`) — свойство, список или вложенный объект
4. `PluginDataMapper.cs` — строка маппинга или присвоения

Пропуск любого пункта приводит к тихому багу: параметр не сохраняется или не передаётся в построение. Компилятор ошибку не покажет.

*Пример маппинга детали:*
```csharp
HeadBeam = CreatePart(data.HB_Profile, data.HB_Material, data.HB_PartPref, data.HB_PartNo, data.HB_AssyPref, data.HB_AssyNo, data.HB_Name, data.HB_Class, data.HB_UDA)
```

## 2. Изоляция Сервисов и работа с Tekla API

### 2.1 Анализ габаритов через Solid (Коллизии)
Запрещено использовать оси `AxisX/AxisY` профиля для вычисления зазоров и коллизий в сложных узлах. Профили могут быть отзеркалены или повернуты. 
* **Паттерн вычисления границ:** Для поиска крайних точек детали всегда используется перебор граней физического тела `part.GetSolid()` с проецированием их на нужный вектор (метод `GetMaxProjection`).

### 2.2 Роль `TeklaComponentService.cs` и Борьба с Автостандартами
Сервис инкапсулирует вставку узлов.
* **Правило Двойного Хука (Double Hook):** При вставке компонента Tekla приоритетно применяет системные AutoDefaults. Для подавления этого поведения паттерн обязует:
1. `component.Insert()`
2. `component.LoadAttributesFromFile(presetName)`
3. Обнуление корней (передача `0` в атрибуты вроде `ac_root`).
4. `component.Modify()`

## 3. Разделение ответственности: Оркестратор, Менеджер и Математика

Код построения геометрии разделен по принципу SOLID:

1. **`ModelPlugin.cs` (Оркестратор)**: Принимает точки вставки, вызывает Менеджер и сервисы, отвечает за транзакции в БД модели.
2. **`Services/JointManager.cs` (Director)**: Внешняя надстройка (бизнес-логика). Анализирует входящие детали, сопоставляет их классы с таблицей UI, фильтрует исключения, вычисляет векторы и упаковывает всё в массив `BraceWrap`.
3. **`Services/NodeGeometryBuilder.cs` (Чистый математический движок)**: Вычисляет пересечения лучей (Ray Intersection). Класс является "слепым" — он не принимает решений о том, какие углы назначить раскосу. Он только исполняет директивы, заложенные Менеджером.

## 4. Экосистема Интерфейса (UIControls)

Интерфейс плагина построен на принципах атомарного дизайна.
* **Сетка выравнивания:** Строгое соблюдение `Grid.ColumnDefinitions`: Столбец 0 (Чекбоксы, MinWidth 25) -> Столбец 1 (Лейблы, Width 200) -> Столбец 2 (Ввод, Width *).
* **Модульность:** Использование атомарных контролов (`PartAttributesRowControl`, `PositioningRowControl`).

## 5. Законы генерации кода для ИИ (AI Instructions)

1. **Запрет на частичный код:** При изменении логики внутри методов ИИ обязан выводить модифицированный метод целиком. Комментарии вида `// Здесь старый код...` запрещены.
2. **Синтаксический парсинг:** Любое текстовое поле с массивами обрабатывается через `StringParserService`.
3. **Строгая типизация углов:** При передаче углов четко разграничивать радианы и градусы (`Deg`, `Rad`).
4. **Конвенция префиксов:** `B_` (Branch), `L_` (Lacing), `S_` (Strut), `HB_` (HeadBeam).
5. **Запрет мутации входных данных:** Сервисные методы не имеют права изменять поля DTO-объектов.
6. **Запрет `out`-параметров:** Возврат множества значений осуществляется через именованные классы или `ValueTuple`.
7. **Разделители секций:** Использовать `// ---`, а не `/// ---`.
